# Project instructions

- Prefer `codebase-memory-mcp` tools for code discovery. Index the repository first if needed, then use the graph to search, trace relationships, and read code snippets. Fall back to file searches for configuration, string literals, or when graph results are insufficient.
- For questions about libraries, frameworks, SDKs, APIs, CLI tools, and cloud services, check current documentation with `ctx7`: run `npx ctx7@latest library <name> "<question>"`, then `npx ctx7@latest docs <libraryId> "<question>"`. Run requests outside the sandbox, omit secrets, and use at most three commands per question. If a quota error occurs, report it and suggest `npx ctx7@latest login` or `CONTEXT7_API_KEY`.
- Create a separate `feature/<n>-<slug>` branch for each task or pull request, where `<n>` is the pull request number and `<slug>` a short name, for example `feature/33-release-v0.1.1`. If the current `master` contains all completed preceding work, branch from it. If `master` is behind, branch from the latest branch in the milestone chain after checking history and refreshing remote references. Do not choose a base by commit date alone: the new branch must continue the existing chain.
- Include the relevant task ID in every commit message using the `KB-<NMM>` format, for example `KB-201: ...`. If a commit covers multiple tasks, include all relevant task IDs.
- Open a pull request only when the user asks for it. Before pushing more commits to an existing branch, check its pull request state with `gh pr view`; if it is already merged, continue on a new branch that follows the milestone chain, because commits pushed after a merge never reach `master`.
- GitHub deletes merged branches automatically. Delete a branch manually (`git push --delete`, `git branch -D`, `gh api` branch deletion) only when its content reached `master` by other commits (squash, cherry-pick, later rework): check `git cherry -v master <branch>` and the diff of every file it changes against `master`, then get the maintainer's confirmation. Refresh stale remote references with `git fetch --prune`.
- Small text-only changes (TODO, DONE, CHANGELOG, docs, behavior reports) may be committed directly to `master` without a branch or pull request. Code and content work still uses a `feature/<n>-<slug>` branch.
- CI runs the full cycle (`package-checks.yml`) only for changes to code, tests, shipped content (`skills`, `commands`, `init`, `core`, `workflows`, `plugins`, `adapters`), or build inputs; text-only changes run the light `docs-check.yml`. Tag pushes and manual runs of `release-candidate.yml` always run the full cycle. When adding a new code or content directory, add it to the path filters in `.github/workflows/check.yml`.
- Size and similar limits (for example the 30–50-line core) are budgets, not prohibitions. When a change needs to exceed one, say so and ask the maintainer to confirm instead of reworking the design to fit; once confirmed, change the limit in `scripts/validate.py` and the documents that state it in the same change.

## TDD red/green commits

- When work is test-driven, commit the failing tests alone first: message `<task ID>: test: ...` (or `test: ... (<task ID>)` where the project ends subjects with the task ID), a line `Expected failing: <test ids>` and the trailer `TDD: red`. Then commit the solution with the same task ID and the trailer `TDD: green`. Documentation, exploratory work and configuration are exempt.
- A red commit fails CI by design: skip push-triggered runs whose head commit message contains `TDD: red` and keep pull-request runs unconditional, or push the pair together.
- Merge with merge commits, not squash, so the pairs stay in history; find the first failing commit with `git bisect --first-parent`.
- Check the pairs with `python scripts/kaboost_audit_tdd.py <range> --run '<test command with {tests}>'`: the named tests must fail on red and pass on green.
